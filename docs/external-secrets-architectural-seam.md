# External Secrets as the Configuration Seam

## Source contracts

The workshop has three sources in `cf-idp-secrets`:

- `platform-bootstrap-config`, generated by Kustomize from `config/platform.env`;
- `platform-target-config`, generated by Kustomize from `targets/workshop/catalog-info.yaml` as
  `platform.yaml`;
- `platform-secrets`, created manually from the ignored `bootstrap/secrets.env` and containing only
  credentials.

Argo CD owns and updates both public configuration Secrets. Target changes therefore flow through
normal Git reconciliation and are never copied into the credential backend.

`ClusterSecretStore/cf-idp-config` and `ClusterSecretStore/cf-idp-secrets` use distinct service
accounts and source contracts. The Kubernetes provider requires namespace-level `get`, `list`, and
`watch` access for store validation, so the workshop backend is a logical separation rather than a
hard confidentiality boundary. Namespace-local ExternalSecrets use per-item store references when
they combine the sources, parse structured YAML with ESO template engine v2, and emit only consumer
keys. A production backend should enforce the equivalent paths independently.

## Stable workload contract and production migration

Workloads know only their namespace-local Secret names and keys. A production profile can replace
the credential store provider with Vault, Conjur, AWS Secrets Manager, Azure Key Vault, or another
approved backend while preserving those contracts. The Git-backed configuration store remains
separate. Use workload identity, audit access and rotation, wait for every ExternalSecret to report
Ready, and then remove the workshop Kubernetes credential source.

The two stores are an architectural boundary, not a claim that a Kubernetes Secret is equivalent to
an enterprise secret manager.

## Consumer inventory

| Consumer | Public configuration | Credentials | Result |
|---|---|---|---|
| Developer Hub | bootstrap primitives + target YAML | backend, GitHub, Keycloak | `rhdh-secrets` with derived service and catalog URLs |
| Keycloak realm | target YAML | realm client secrets, demo password | realm placeholder Secret |
| Quay | target YAML | admin identity/password | `quay-config` bundle and bootstrap Secret |
| Gitea (optional) | target YAML | application/admin secrets | runtime config and credential Secrets |
| Pipeline Microcks task | target YAML | Microcks service-account secret | URL/client Secret pair |
| Microcks chart | Git Helm overrides | MongoDB credentials | render-time endpoints + referenced MongoDB Secret |
| Dev Spaces | none | GitHub OAuth client | local OAuth Secret |

Apicurio ingress hosts and `QuayIntegration.spec.quayHostname` are the documented direct scalar
exceptions. Keycloak and Gitea use generated Route names; their component manifests contain no
installation hostname.
